# 평가 기준

PRD 17장이 요구하는 «Precision·Recall의 분모, 정답 라벨 규칙, 제외 기준»을 여기에 고정한다.
이 문서를 고치지 않고 숫자만 좋아지는 변경은 받아들이지 않는다.

```bash
npm run eval
```

기준 미달이면 종료 코드 1로 끝난다. 파서·규칙을 바꿨으면 반드시 다시 돌린다.

---

## 1. 평가 데이터

`fixtures/golden.json` — **합성 데이터**다. 실제 쿨메신저 원문은 저장소에 들어가지 않는다
(PRD 22장). 실제 쪽지 3,236건을 분석해 얻은 **표현의 분포만** 본떠 새로 썼고, 사람 이름·
학교명·연락처·학번은 전부 가공값이다.

케이스는 실제 데이터에서 관찰된 비율에 맞춰 골랐다.

| 묶음 | 사례 수 | 실제 데이터에서의 비중 |
|---|---|---|
| 절대 날짜 (`N월 N일`, `N/N`, `YYYY-MM-DD`) | 4 | 15.3% / 7.9% / 2.6% |
| 상대 날짜 (`오늘`·`내일`·`모레`) | 3 | 13.8% / 6.4% / 0.1% |
| 요일만 적힘 | 2 | 6.9% |
| 이번 주·다음 주 | 1 | 4.5% |
| 교시 | 1 | 6.8% |
| 기간 | 1 | 1.2% |
| 모호 표시 (연도 생략·오전오후·요일 불일치) | 3 | — |
| 선택 행사 | 1 | 관찰됨 |
| 변경·취소 | 3 | 3.8% / 0.3% |
| 대상 적합·부적합 (`3학년 담임` 등) | 3 | 22.7% (학년), 13.5% (담임) |
| 긴급 공지 | 1 | 관찰됨 |
| 잡담·단순확인 | 3 | 30.2% / 0.7% |
| 민감정보 | 3 | 1.4% |
| 날짜 아님 (전화번호·내선) | 2 | — |

**골든셋이 100%라는 말은 «정확도가 100%»라는 뜻이 아니다.** 이 사례들에 대해 회귀가 없다는
뜻이다. 실제 정확도는 교사 파일럿에서 사람이 라벨을 붙여야 알 수 있다.

## 2. 정답 라벨 규칙

라벨은 **문장 단위**로 붙인다. 한 쪽지를 하나의 라벨로 고정하지 않는다 (PRD 9장).

| 라벨 | 붙이는 조건 |
|---|---|
| `OFFICIAL_EVENT` | 학교가 치르는 행사·회의·연수. 참석 의무가 있거나 «실시합니다»류 서술어가 붙는다 |
| `DEADLINE` | 사용자가 하는 제출·신청·입력이면서 기한 표현(`까지`, `마감`)이 있다 |
| `PERSONAL_TASK` | 사용자가 하는 행동이지만 기한 표현이 없다 |
| `OPTIONAL_EVENT` | 같은 쪽지 안에 희망·신청자 대상 표현이 있다 |
| `REFERENCE_NOTICE` | 날짜는 있으나 사용자 행동도 참석 의무도 없다 |
| `URGENT_NOTICE` | 당일 안전·기상·시설 공지. 행사 이름이 없다 |
| `PERSONAL_CHAT` / `ACK_REPLY` | 인사·감사·단순 확인. **날짜가 들어 있어도 행동 의무가 없으면 여기다** |
| `SENSITIVE` | 주민번호·계좌·비밀번호 값·상담/건강 내용이 보인다 |

경계 사례를 판단한 근거:

- **`계기교육을 실시합니다`** → `OFFICIAL_EVENT`. 학교가 치르는 일정이지 내 개인 업무가 아니다.
- **`내일도 좋은 하루 보내세요`** → `PERSONAL_CHAT`. «내일»이 있어도 일정이 아니다.
- **`8월 20일 진행된 협의회 결과 공유`** → 후보 없음. 쪽지는 최근이지만 일정 날짜가 지났다.
- **`저는 8월 31일 개인 출장입니다`** → `REFERENCE_NOTICE`. 제3자의 개인 일정이라 등록하지 않는다.

## 3. 지표의 분모

### 공식 일정 Precision (목표 95% 이상)

```
분자 = 정답이 OFFICIAL_EVENT·DEADLINE·PERSONAL_TASK 이고 예측도 같은 사례 수
분모 = 예측이 OFFICIAL_EVENT·DEADLINE·PERSONAL_TASK 인 사례 수
```

**분모는 «예측»이 기준이다.** 일정이라고 내놓은 것 중 몇 개가 진짜였는지를 본다.
놓친 일정은 이 지표에 들어가지 않는다.

### 민감정보 격리 Recall (목표 99% 이상)

```
분자 = 민감 사례 중 후보를 하나도 만들지 않은 수
분모 = 정답이 SENSITIVE 인 사례 수
```

의심스러우면 격리하는 쪽이 맞다. 이 지표에서 Precision은 일부러 보지 않는다.

### 잡담 오탐률 (목표 3% 미만)

```
분자 = 정답이 «후보 없음»인데 후보가 하나라도 나온 사례 수
분모 = 정답이 «후보 없음»인 사례 수
```

## 4. 평가에서 빼는 것

다음은 «틀렸다»로 세지 않는다. 규칙대로 동작한 결과이기 때문이다.

- **일정 날짜가 이미 지나 후보가 안 생긴 경우.** 가장 흔한 «후보가 왜 없지?»의 정답이다.
- **가져오기 기간(기본 14일) 밖이라 읽지 않은 쪽지.**
- **역할 태그가 비어 있어 «나와 관련 없음»으로 걸러진 경우** (기술계획서 8.9).
  단, 이는 **대상이 적혀 있는 쪽지**에만 해당한다. 대상이 아예 안 적힌 쪽지는 나에게 온
  것으로 보고 통과시킨다 — 「모레까지 명렬표를 제출해 주세요」가 걸러지면 안 된다.
- **모호 표시가 붙어 자동등록되지 않은 경우.** 후보함에 올라왔다면 정상이다.
- **인용문만 있는 쪽지.**
- **`아주 확실한 것만` 단계라서 자동등록되지 않은 경우.** 이 단계는 실제 쪽지에서 거의
  발동하지 않는 것이 정상이다 (기술계획서 7.6).

## 5. 아직 측정하지 않는 것

정직하게 적어 둔다. 아래는 이 골든셋으로 알 수 없다.

- **Recall(놓친 일정 비율).** 실제 쪽지에 «진짜 일정이 몇 개 있었는지»에 대한 사람 라벨이
  없어서 분모를 만들 수 없다. 교사 파일럿에서 사람이 라벨을 붙여야 한다.
- **제목 품질.** 사람 평가가 필요하다. 현재는 «틀린 긴 제목보다 짧고 맞는 제목»을 택했다.
- **하루 알림 5건 이하** 목표. 알림 모듈이 붙어야 잰다.
- **성능 기준** (5,000건 10초). 현재 3,388행 처리에 수 초가 걸리지만 Rust 이식 후 다시 잰다.
- **자동 등록 단계의 «적절함».** 두 단계가 서로 다르게 동작하는지는
  `test/policy.test.ts` 가 같은 파일 하나로 검증한다 (기술계획서 7.6이 요구한 테스트).
  다만 «3건이 맞는 수인가»는 사람이 라벨을 붙여야 알 수 있다.

## 6. 실제 데이터에 돌렸을 때 (참고 수치)

`coolexcel/` 실제 파일 7개, 기준일 2026-08-28, 가져오기 기간 14일:

```
행 3,388건 → 기간 밖 3,088 · 중복 140 · 인용문만 7 · 격리 1
→ 실제 처리 153건 → 일정 날짜 지남 149 → 후보 15건

자동등록 가능:  분명한 일정까지 5건  /  아주 확실한 것만 0건
```

후보가 적은 것은 고장이 아니다. 「쪽지는 최근인데 그 안의 날짜가 지났다」가 149건으로
가장 큰 몫이고, 이건 기술계획서 7.2가 예고한 정상 동작이다.
